A slide-generating agent, improved with Google's Harness²

Project report · 2026-10-29 · judge of record: OpenAILLM:gpt-6-astra

Summary

  • What was built: a local, tool-calling slide agent (Gemma 4 via Ollama, python-pptx output), connected to Google Research's Harness² through a custom benchmark adapter, a pluggable improver, and a separate GPT-6 Astra judge. Harness² was made to run natively on Windows with three small patches.
  • Experiment: the full Harness² loop on two business tasks at --k 2, run twice with the same slide-writing model (Gemma) and the same 4 baseline decks, changing only the improver: local gemma4, then OpenAI's gpt-6-luna.
  • Outcome: with Gemma as improver, the adopted harnesses scored +0.5 and 0 points over the baseline (out of 25), which is noise. With Luna they scored +0.5 and +2.0, the first gain that reaches the ±1-point noise band's edge. Across all 12 decks from each improver's harnesses, the averages were 13.1 (Luna) vs 12.7 (Gemma) vs a 12.75 baseline. This is suggestive, not conclusive: one sample per harness.
  • Main finding: the improver decides what gets optimized. Gemma pushed the harness toward persuasive "mandates" that the judge penalized as inaccurate. Luna pushed it toward slide-count discipline and source fidelity, adding an hr_survey_deck skill that reads like a list of the judge's own complaints. Its selector also chose on fidelity, where Gemma's chose on slide count.
  • Cost: Luna's improver calls cost about $0.05 for the whole run (305k tokens). Judging with GPT-6 Astra was the larger API cost.

⚠ Potential conflict: the improver and the judge are both OpenAI models

In the Luna run, the model that rewrote the harness (gpt-6-luna) and the model that scored the results (gpt-6-astra) come from the same provider and likely share training data and notions of what a good deck looks like. A harness that Luna considers better may score higher with Astra partly because the two models agree with each other, not only because the decks got better for a human audience. That would overstate Luna's advantage over Gemma.

The design limits but does not remove this risk. The improver never sees scores or the rubric; Harness² forbids words like "score" and "rubric" in the improver's prompts; and the judge's main complaints (misstated statistics, invented causation) can be checked against the source document.

We will address this in future work by testing improvers from other model families against the same judge, for example Anthropic's Claude, Google's Gemini, or local models already installed here such as gpt-oss:20b and qwen3, and by cross-checking results with a judge from a different family than the improver.

Findings

1. The improver decides what gets optimized

Harness² never shows the improver a score, so it can only optimize what it can see in the trajectories and decks. Gemma rewarded visible structure: both of its adopted harnesses converged on a "mandatory persuasive narrative arc" with business-risk framing, and the judge penalized the resulting distortions. Every remote-work deck from Gemma's harnesses scored 1/5 for accuracy. Luna spotted that the agent kept adding an unplanned seventh slide after the critique step, made the requested slide count binding, and on the survey task added a skill whose rules include "do not turn a survey finding into a causal claim" and "preserve qualifiers such as 'likely'". That deck was the only remote-work deck in either run to reach 2/5 for accuracy, and it scored 14/25 against a 12/25 baseline.

2. Luna was more careful about evidence, and that emptied the library

For every edit, Luna marked the verdict confounded, because each candidate changed several files at once and so no single contrast isolates an edit. Following Harness²'s instructions for that case, it then declined to write a lesson (NO_ENTRY) on both tasks. Gemma, given the same instructions, marked every edit "helped" and wrote "high confidence" lessons. Luna's behavior is the correct one, but it meant the library stayed empty and nothing carried over from task 1 to task 2, so the Luna run tests single-task improvement only.

3. The selectors chose differently

Gemma's selector decided both tasks on conformance to the slide count ("7 slides vs 8"). Luna's weighed fidelity: "B invents a three-month pilot duration… not requested or supported"; "A… calls the burnout decrease 'significant,' which the source does not establish". In all four selections the chosen final was the one the judge rated higher, but Luna's reasons are the kind a human reviewer would give.

4. The slide-writing model still caps quality

All 28 decks scored 11–16 out of 25. The best deck of the project was a Luna candidate (rag-for-execs/dom2, 16/25), but it was not one of the composed finals Harness² can adopt. Accuracy remains the weakest criterion in every group (means of 1.25 base, 1.42 Gemma-improved, 1.58 Luna-improved). Guidance text can reduce errors, but a 4B-class model still misreads statistics; a stronger executor or a fidelity tool is needed for larger gains.

5. Evaluation hygiene changed the conclusions

Several design choices changed the conclusions along the way:

  • a judge from a different family than the executor (self-grading Gemma gave all 5s);
  • points instead of a pass mark (a 4/5 pass mark hid every difference);
  • checking Harness²'s fell_back records (one resumed run silently used the base harness everywhere yet still wrote a confident lesson);
  • a shared, reused baseline, so both improvers are compared against identical base decks and scores rather than two noisy re-judgings.

Gemma's improver also never saw its full evidence: its 60k-character budget dropped files from every composition prompt. Luna saw everything.

Recommended next steps

  1. Test improvers from other model families (Claude, Gemini, gpt-oss:20b, qwen3) against the same judge, and cross-check with a judge from a different family than the improver. This addresses the same-provider conflict above.
  2. Un-confound the edits so lessons can be recorded: use --mode sequential, or have candidates change one component at a time, so the improver can attribute effects and fill the library.
  3. Repeat with more samples (more tasks, the technical domain, higher --k) before treating a 2-point gain as real.
  4. Give the agent a fidelity tool, for example a critique check that compares every number on a slide against the source, so Harness² has a mechanism it can strengthen.
  5. Keep one pinned judge for every comparison, and treat differences under about 2 points as noise.

1. What was built

The slide agent

A deliberately simple Python agent (slide_agent/) that turns a topic, an audience and an optional source document (.txt, .md, .pdf) into a PowerPoint deck. It runs on a local model, gemma4:latest through Ollama, using a tool-calling loop: each turn the model replies with one JSON object, {"thought", "tool", "args"}. The agent runs the tool and returns the result as the next message. This JSON protocol works with models that have no native tool calling, and switching providers means adding one class to slide_agent/llm.py.

Tools: read_source, plan_outline, add_slide, edit_slide, delete_slide, view_deck, critique_deck (rule-based checks against the best practices) and save_deck (python-pptx, with speaker notes). It is intentionally unoptimized: no retries, no context trimming, a rule-based critique. That leaves room for a harness optimizer to find improvements.

The Harness² integration

Harness² (Google Research, Apache 2.0) improves the harness around a fixed model (prompts, guardrails, memory, tool guidance, skills) without changing model weights. To connect our agent, the guidance text moved out of code into editable files in harness_base/, and a custom benchmark was written against Harness²'s BenchmarkAdapter protocol.

2. How Harness² works

1 · BaseRun the agent with the unmodified harness (twice at --k 2).
2 · ProposeThe improver reads the trajectories and decks and edits the harness: inv candidates make general edits, dom candidates make domain-specific edits.
3 · ProbeRe-run the same task with each candidate harness.
4 · ComposeMerge what seemed to help into agg finals, run them, and let the selector (the improver model) pick one with a written reason.
5 · RememberStore the adopted harness and a cue/lesson/evidence entry in a per-domain library that later tasks read.

No step uses a ground-truth score. The improver and the selector judge only from the evidence, and the benchmark prompts are not allowed to mention "score", "rubric" or "grader". A separate judge scores the outcome afterwards, so we can measure whether the harness actually improved.

3. Experiment setup

  • Domain: business, 2 tasks run in order: rag-for-execs (a pitch to non-technical executives) and remote-work-findings (a deck for HR leadership built from a survey document). The second task starts with the first task's lesson in the library.
  • Budget: --k 2 --mode parallel, giving 8 rollouts per task (2 base, 2 inv, 2 dom, 2 agg).
  • Improvers compared (2): ollama:gemma4:latest (gemma4 (local)), openai:gpt-6-luna (gpt-6-luna (OpenAI)). Every run starts from the same 4 base rollouts, with their judge scores reused rather than re-judged, so the improvers are compared against an identical baseline. That makes 28 distinct decks in total.
  • Executor: gemma4:latest (local) in every run. Judge: OpenAILLM:gpt-6-astra.
  • Scoring: rules passed out of 8, plus rubric points out of 25 (story, assertion titles, audience fit, accuracy, speaker notes). Re-judging the same deck varies by about ±1 point, so smaller differences are noise.

gemma4 (local) · rag-for-execs

  • cue: When generating persuasive content for a high-stakes, non-technical audience (e.g., executives) that requires a specific, multi-stage argument (e.g., technology adoption).
  • lesson: The system's long-term memory and system prompt must enforce a rigid, multi-stage narrative structure (Problem → Solution → Value → CTA) and simultaneously inject domain-specific constraints (e.g., "must use ROI language," "must avoid jargon") to ensure the content is both structurally sound and contextually relevant to the audience's priorities.
  • evidence: The combination of the structural mandates from inv2 (enforcing the mandatory narrative arc in systemprompt.md) and the domain-specific content guidance from dom2 (defining the required narrative arc and vocabulary in LongTermMEMORY.md). This combination resulted in the agg1 rollout, which demonstrated a perfect blend of structural rigor and executive-level business focus.
  • confidence: high, because the successful output (agg1) is a direct and visible result of combining these two distinct types of constraints (structural enforcement and domain knowledge injection).

5. Engineering log

Decisions

  • Local executor, API judge, configurable improver. Gemma writes every deck for free on the local GPU. The judge is an API model from a different family than the executor. The improver can be local or an API model; with gpt-6-luna it costs fractions of a cent per call.
  • JSON tool protocol instead of native tool calling, because Gemma's native support in Ollama is uneven, and the protocol keeps the agent provider-agnostic.
  • Custom benchmark instead of the built-in ones. LAB, JobBench and WorkBuddy test coding agents on legal, professional and office work. Our agent needed its own adapter, modelled on the repo's demo.py.
  • Points instead of pass/fail. A 4/5 pass mark made every deck score 8/13 once the judge became strict, which hid all differences.
  • A shared, reused baseline. The base mean averages all base rollouts, and every improver is compared against the same base decks and scores.

Making Harness² run on Windows

Harness² targets Linux. The core needed three small patches (in vendor_harness2/):

  1. core/schedule.py: fcntl (POSIX file locking) falls back to msvcrt.
  2. core/tree.py, core/runmark.py, core/proposer.py: relative paths use as_posix(). Windows backslashes had made the improver's edits invisible to the probes.
  3. core/context.py: evidence folders are deleted with a handler that clears read-only flags and retries. OneDrive marks synced folders read-only, and Windows refuses to delete a read-only directory, which made every stage silently fall back to the base harness.

Bugs found and fixed in our own code

  • The selector wrote context/candidates/A.md instead of the bare ID A, and sometimes left out the <why> tags. Replies are now normalized, and the prompt shows the format.
  • Improver workspaces and audit files were keyed by label only, so labels like inv1.a1 collided across tasks. They are now keyed by mode and task.
  • Without a reply cache, a resumed run would draw new edits while reusing rollouts from the old ones. The proposer now caches under upstream's _call_fingerprint, plus the model name.
  • Gemma's 60k-character evidence budget silently left 4–12 files out of every composition prompt and 54 files out of a lesson-writing prompt. API improvers now see the full folder.
  • A blank OPENAI_BASE_URL= in .env became an empty API address. The loader now skips blank values.
  • Runs now live outside OneDrive (for example ~/harness2_runs/). Thousands of scratch files shouldn't sync, and synced folders turn read-only.
